# TV-Next P0–P6 acceptance gates

**A committed feature is not proof of a working feature.** Implementation completion requires reproducible automated evidence, compatibility fixtures and updated docs. Per explicit user instruction (2026-10-25), implementation issues may close after code/automated acceptance, while physical-device testing stays in a separate open issue. P1 physical acceptance is #38; release acceptance still requires applicable device/security/signing evidence.

## Required for every PR

1. Provide scope, supported platforms, reproduction steps and known limits.
2. Run all affected CI checks (Web typecheck/unit tests, Kotlin Gradle tests/bootJar, macOS simulator build when Swift changes).
3. Add success, failure and boundary tests; never use third-party streams as unapproved automated test dependencies.
4. Review no credentials, tokens, unauthorized sources or unsafe plugin execution are bundled.
5. Update OpenAPI/compatibility matrix, docs and issue acceptance checklist.
6. Distinguish verified physical hardware/media tests from compilation or simulator smoke tests.
7. Never publish a signed release or mark a phase complete without verifiable evidence.

## Release hold

If Apple devices, authorized external fixtures, signing credentials or independent security review are unavailable, mark **BLOCKED**; never invent passed tests, signed IPA artifacts or App Store approval. Physical checks and release decisions require verifiable access.

### Web dependency reproducibility evidence

Web dependencies now use a committed npm v3 lockfile generated by Node 22/npm on a GitHub-hosted runner, instead of resolving new transient versions on every build. Web CI and the Web Dockerfile both run `npm ci`, which refuses a package/lock mismatch. This improves reproducibility but is **not** an SBOM, lockfile audit or guarantee that registries and base images remain available. Docker base image digest pinning, dependency security scans and release provenance remain P6 tasks.
