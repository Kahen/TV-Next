# Native iPhone/iPad WebDAV (P4 read-only slice)

Issue: [#66](https://github.com/Kahen/TV-Next/issues/66); parent [#5](https://github.com/Kahen/TV-Next/issues/5).

## Supported subset

Open **功能导航 → WebDAV 文件**, enter an authorized WebDAV directory URL, optionally enter username/password, and tap **连接 WebDAV**. The SwiftUI client issues RFC 4918 `PROPFIND` with `Depth: 1` and displays at most 200 immediate child entries (folders first). Navigate folders or select a supported media file. The current-folder **刷新当前目录** action reissues the same bounded Depth:1 PROPFIND; failures leave the previous listing visible, and superseded requests cannot overwrite newer results. A local case-insensitive filename filter and media-only toggle narrow the already returned entries; folders remain visible in media-only mode. Search does not send the filter to the server and cannot find entries beyond the first 200. Changing folders resets the filename filter; disconnecting clears the filter and toggle. No remote media sources are bundled. This is a native WebDAV client; it does not execute FongMi/TV Android WebDAV/Spider plugins. AList/OpenList remains a separate cloud integration.

Supported playback candidates by suffix: MP4, M4V, MOV, HLS M3U8, MP3, M4A, AAC and TS. Actual AVPlayer decoding, streaming, range requests and HLS compatibility depend on the server and device. Unsupported files remain visible but cannot be selected. No uploads, writes, deletes, WebDAV locks, pagination beyond 200 entries, WebDAV digest authentication, SMB, download/offline cache or multi-account persistence.

## Credentials and network boundaries

- The root URL must be HTTP(S), without URL-embedded user/password, query or fragment. Basic authentication is allowed only for HTTPS, with the credentials held in SwiftUI memory until the view disappears or the user disconnects. Do not paste passwords into the URL. HTTP is only allowed without credentials.
- Directory listings use an ephemeral URLSession with redirects rejected and a 15-second timeout. The redirect delegate reports the original HTTP 3xx even if URLSession completes the denied redirect without a subsequent response callback. Only same-origin, immediate children within the configured root are accepted; encoded slash, traversal, foreign-host and deeper-path entries are discarded. The RFC 4918 XML collector reads only direct DAV:response/DAV:href, requires a successful 2xx DAV:propstat with DAV:resourcetype, and trusts DAV:collection only inside that successful property; failed properties, failed response statuses, missing statuses, nested/foreign namespace spoofing and malformed status lines are not listed. Nonconforming servers omitting propstat status are intentionally unsupported. The parser rejects XML DTD/entities and responses above 1 MiB. Native PROPFIND now uses a cancelable `URLSessionDataDelegate` to read bounded chunks, rejecting a declared `Content-Length` above 1 MiB before body consumption and rejecting unknown-length transfers before a chunk would push the accumulated XML above 1 MiB. The limit applies to the bytes delivered to the app; URLSession/OS internal transport buffers and total network traffic are not independently bounded.
- Public media is handed to the existing AVPlayer path. Media needing Authorization headers uses the existing authenticated home-server media capability relay; **log in to the home server first**. Credentials are not passed as unsupported private AVPlayer asset options and are not stored in UserDefaults. The existing library snapshot strips private headers and requires re-authentication after relaunch. **Disconnect, view dismissal or switching WebDAV roots stops any matching playback, cancels pending relay creation, closes an active capability and removes matching in-memory recent/library records** so a retry cannot reuse Basic credentials. This is a deliberate playback interruption, not merely a form reset. The home server must be able to reach the WebDAV endpoint and enforce its own SSRF/DNS/redirect and resource quotas.
- Directory URLs and filenames can reveal private structure. Do not expose this screen or the home server to untrusted users. The media relay is not an independent security audit or an authorization guarantee for arbitrary servers.

## Reproducible automated verification

`swiftc -warnings-as-errors TVNext/NativeWebDAV.swift tests/WebDAVSmoke.swift -o /tmp/webdav-tests && /tmp/webdav-tests` from `apps/ios` validates the synthetic RFC 4918 response and rejected cross-origin/traversal/encoded slash paths, invalid root URLs, insecure Basic auth, DTD and oversized XML. The macOS CI also starts `scripts/webdav_fixture_server.py` bound to `127.0.0.1:8767` and executes `WebDAVNetworkSmoke.swift` to verify actual Depth:1 PROPFIND, foreign-link filtering, refusal of both same-origin and cross-origin HTTP redirects (with deterministic original 302 status) and refusal of credentials over HTTP. The parser regression additionally verifies 200/404 mixed propstat responses, direct href scoping, foreign namespaces, failed response statuses and absent/malformed statuses. The streaming-cap regression additionally verifies valid unknown-length responses, declared oversized responses, unannounced oversized responses and successful subsequent requests; the parser smoke accepts exactly 1 MiB and rejects 1 MiB + 1 byte. The iPhone/iPad Xcode scheme runs `NativeWebDAVTests`, `MediaLibraryTests` credential-revocation and retry regression cases, and production `LibraryUITests.testNativeWebDAVFormRejectsUnsafeURLWithoutNetworking` in the full integration gate. Link the final HEAD and successful Actions runs for this RFC 4918 follow-up to Issue #72 before closing it.

No physical iPhone/iPad, third-party WebDAV service, authenticated media relay end-to-end, Apple signing, independent security audit or release result is claimed by these fixtures. Physical acceptance remains [#38](https://github.com/Kahen/TV-Next/issues/38) and P4/P5/P6 gates.

## URLSession completion fallback and synthetic CI regression (#74)

The main-branch aggregate workflow [40809764313](https://github.com/Kahen/TV-Next/actions/runs/40809764313) showed a sporadic iPad-only `NativeWebDAVError.invalidResponse` in the localhost network smoke while iPhone and all non-iOS checks passed. Native `URLSessionTask.response` may hold the final HTTP response when a separate `didReceive(response:)` callback was not delivered. The completion fallback now applies the **same** 207-only, 401/403 and declared-length rejection policy before returning any XML; redirects remain explicitly denied and 1 MiB incremental data checks remain active. If there is no validated HTTP response, the client still fails closed.

The localhost fixture explicitly closes responses without `Content-Length`. The native smoke exercises 207 valid XML, empty 207 XML, 200, 302 local/external redirects, 401/403, 404, declared and streamed 1 MiB overflow, a valid unknown-length response and recovery after a rejected transfer. Status/size classification also has direct positive/negative/boundary Swift assertions. These are synthetic transport tests, not physical Apple-device or third-party WebDAV validation. See [Issue #74](https://github.com/Kahen/TV-Next/issues/74) for the final-head CI evidence; a passing PR gate is required before merge.


## Local WebDAV browse controls (P4, #76)

Native Swift smoke and XCTest verify trimmed case-insensitive matching, folder retention, supported/unsupported suffixes, and empty results. Production iPhone/iPad XCUI checks invalid URL rejection and, against the owned localhost RFC 4918 fixture, a successful folder listing, media-only folder retention, case-insensitive search, same-folder refresh, and disconnect cleanup. Existing Swift network smoke verifies bounded Depth:1 transport. No real WebDAV provider, large-directory server-side search or physical-device behavior is claimed.

## Bounded native breadcrumb navigation (P4, #78)

When browsing a nested WebDAV directory, the iPhone/iPad SwiftUI view displays horizontally scrollable root/ancestor shortcuts in addition to **上级目录**. Each shortcut reuses a validated, canonical ancestor URL under the connected root; labels are not concatenated into requests. Breadcrumb generation is capped at 32 directory levels and returns no shortcuts for invalid, outside-root, non-directory or over-depth inputs. Moving to an ancestor uses the existing cancelable, bounded Depth:1 PROPFIND and resets the local filename search. Swift smoke/XCTest cover root, nested, foreign-origin, sibling, file URL and depth boundaries. Production iPhone/iPad XCUI navigates into an owned localhost folder and back to root. This is not server-side search, SMB/DLNA, or physical-device/provider verification.

### Localhost streaming fixture portability regression (PR #79)

The initial PR gate [40844912548](https://github.com/Kahen/TV-Next/actions/runs/40844912548) reached the WebDAV network smoke on both Apple simulators but returned `invalidResponse` for the synthetic oversized unknown-length HTTP/1.0 EOF stream. This is a **failed** gate, not evidence of a client-side cap failure or a successful overflow rejection. The owned fixture now emits explicit HTTP/1.1 chunked framing with sixteen 64-KiB chunks followed by a one-byte overflow, so the transport's incremental byte cap is tested without ambiguous EOF framing. A fresh final-head gate is required before merging.

The PR review also identified equivalent-origin URL serialization (explicit default HTTPS port, host casing) as a breadcrumb edge case. Ancestor termination now compares root-validated decoded path segments and always substitutes the configured canonical root URL. Swift smoke and XCTest include those aliases; an unverified PR check does not establish simulator success.
